# Data specification

Backend data will be stored in Postgres.
The structure of this data can be found in [schema.sql](schema.sql).

All [UUID v7] values are generated as column defaults within the database.

## Common scripts for accessing data

### See all posts

```sql
SELECT * FROM posts
```

### Top-level Comments of a Post, without replies

```sql
SELECT * FROM comments
WHERE 1=1
    AND post_id = :post_id
    -- Top-level comments have no parent comment
    AND parent_comment_id IS NULL
```

### Returning the comment tree for a Post

Use the `get_comment_tree` stored function (see [schema.sql](schema.sql) for its definition):

```sql
SELECT
    id,
    post_id,
    parent_comment_id,
    author,
    body,
    created_at,
    updated_at,
    vote_score,
    depth
FROM get_comment_tree(
    p_post_id := :post_id,
    p_max_depth := 2,
    p_page_size := 10,
    p_cursor_id := NULL  -- pass last top-level comment id for next page
);
```

- Returns top-level comments with recursive replies up to `p_max_depth` levels.
- Pagination is **keyset/cursor-based** on top-level comments: pass `p_cursor_id` (the `id` of the last top-level comment from the previous page) to fetch the next page, or `NULL` for the first page.
- Replies within each parent are always returned from the beginning (not cursor-paginated); use `get_reply_tree` for deeper pagination.

### Returning the reply tree for a Comment

Use the `get_reply_tree` stored function (see [schema.sql] for its definition):

```sql
SELECT
    id,
    post_id,
    parent_comment_id,
    author,
    body,
    created_at,
    updated_at,
    vote_score,
    depth
FROM get_reply_tree(
    p_post_id := :post_id,
    p_comment_id := :comment_id,
    p_max_depth := 2,
    p_page_size := 10,
    p_cursor_id := NULL  -- pass last direct reply id for next page
);
```

- The target comment must match both the given `p_post_id` and `p_comment_id`; an empty result set means the comment was not found (backend should return 404).
- The target comment itself is **not** included in the results; only its replies are returned.
- Pagination is **keyset/cursor-based** on direct replies: pass `p_cursor_id` for subsequent pages, or `NULL` for the first page.
- Replies are fetched recursively up to `p_max_depth` levels deep.

# Specification for the shared database

All backend implementations share a single PostgreSQL instance running from the Docker image defined in this directory. Backends communicate with it directly; no other service interacts with the database.

## Docker image

The image is built from `postgres:18` and initializes itself on first start by running `schema.sql`. An optional `load_fixtures` build argument (default `false`) copies `fixtures.sql` as a second init script, seeding the database with sample data.

```
docker build --build-arg load_fixtures=true -t mlad-db .
```

## Primary keys and UUIDs

All tables use [UUID v7] as their primary key, generated by the `uuidv7()` extension function. Backends must treat all IDs as opaque strings and must never generate IDs themselves - the database is the sole source of IDs.

## Tables

### `users`

Stores registered user accounts.

| Column          | Type         | Constraints                 |
| --------------- | ------------ | --------------------------- |
| `id`            | UUID         | PK, default `uuidv7()`      |
| `email`         | VARCHAR(255) | UNIQUE NOT NULL             |
| `username`      | VARCHAR(100) | UNIQUE NOT NULL             |
| `password_hash` | TEXT         | NOT NULL                    |
| `created_at`    | TIMESTAMPTZ  | default `CURRENT_TIMESTAMP` |

Passwords must be stored as a secure hash (Argon2, bcrypt, or PBKDF2). Plaintext passwords must never be stored.

______________________________________________________________________

### `sessions`

Stores active and expired login sessions. A session row is created on each successful login.

| Column       | Type        | Constraints                                      |
| ------------ | ----------- | ------------------------------------------------ |
| `id`         | UUID        | PK, default `uuidv7()`; used as the Bearer token |
| `user_id`    | UUID        | FK --> `users(id)` ON DELETE CASCADE             |
| `created_at` | TIMESTAMPTZ | default `CURRENT_TIMESTAMP`                      |
| `expires_at` | TIMESTAMPTZ | NOT NULL                                         |
| `is_active`  | BOOLEAN     | NOT NULL, default `TRUE`                         |

The session `id` is the Bearer token returned to the client on login. Backends validate a token by looking up a session row where the `id` matches, `is_active = TRUE`, and `expires_at > NOW()`. Logout sets `is_active = FALSE`.

Sessions expire after 30 days by default.

______________________________________________________________________

### `posts`

Stores user-submitted posts.

| Column       | Type        | Constraints                 |
| ------------ | ----------- | --------------------------- |
| `id`         | UUID        | PK, default `uuidv7()`      |
| `title`      | TEXT        | nullable                    |
| `body`       | TEXT        | NOT NULL                    |
| `author_id`  | UUID        | FK --> `users(id)`          |
| `created_at` | TIMESTAMPTZ | default `CURRENT_TIMESTAMP` |
| `updated_at` | TIMESTAMPTZ | default `CURRENT_TIMESTAMP` |
| `vote_score` | INTEGER     | NOT NULL, default `1`       |

`title` is optional - a post may have a body only. `vote_score` is maintained automatically by database triggers (see [Votes](#votes) below); backends must not write to it directly.

Deleting a post cascades to all comments on that post (via the `comments.post_id` foreign key).

______________________________________________________________________

### `comments`

Stores comments on posts and replies to other comments.

| Column              | Type        | Constraints                                       |
| ------------------- | ----------- | ------------------------------------------------- |
| `id`                | UUID        | PK, default `uuidv7()`                            |
| `post_id`           | UUID        | FK --> `posts(id)` ON DELETE CASCADE              |
| `parent_comment_id` | UUID        | FK --> `comments(id)` ON DELETE CASCADE, nullable |
| `author_id`         | UUID        | FK --> `users(id)`                                |
| `body`              | TEXT        | NOT NULL                                          |
| `created_at`        | TIMESTAMPTZ | default `CURRENT_TIMESTAMP`                       |
| `updated_at`        | TIMESTAMPTZ | default `CURRENT_TIMESTAMP`                       |
| `vote_score`        | INTEGER     | NOT NULL, default `1`                             |

`parent_comment_id` is `NULL` for top-level comments (direct replies to a post) and non-null for replies to other comments. The tree has no enforced depth limit at the database level.

Deleting a comment cascades to all of its replies (via `parent_comment_id`) and to all child comments transitively.

`vote_score` is maintained automatically by triggers; backends must not write to it directly.

______________________________________________________________________

### `object_types`

A lookup table for the polymorphic vote system. Seeded at schema load time.

| Column       | Type         | Constraints |
| ------------ | ------------ | ----------- |
| `name`       | VARCHAR(100) | PK          |
| `table_name` | VARCHAR(100) | NOT NULL    |

Pre-seeded rows:

| `name`    | `table_name` |
| --------- | ------------ |
| `Post`    | `posts`      |
| `Comment` | `comments`   |

______________________________________________________________________

### `votes`

Stores individual votes cast by users on posts or comments.

| Column        | Type        | Constraints                     |
| ------------- | ----------- | ------------------------------- |
| `voter_id`    | UUID        | FK --> `users(id)`              |
| `object_id`   | UUID        | The ID of the voted-on resource |
| `object_type` | VARCHAR(20) | FK --> `object_types(name)`     |
| `vote_value`  | SMALLINT    | NOT NULL, CHECK `IN (1, -1)`    |

The combination `(object_id, object_type, voter_id)` is unique - each user may hold at most one vote per resource.

`vote_value` is constrained to `1` (upvote) or `-1` (downvote). A value of `0` is not stored; backends implement "unvote" by deleting the row.

## Triggers

### Vote score maintenance

Three triggers keep `vote_score` on `posts` and `comments` in sync with the `votes` table:

- **`trg_update_vote_score`** - fires `AFTER INSERT OR UPDATE ON votes`. Recalculates `vote_score` on the affected object by summing all `vote_value` rows for that `(object_id, object_type)`.
- **`trg_update_vote_score_on_delete`** - fires `AFTER DELETE ON votes`. Same recalculation using `OLD` (since `NEW` is null on delete).

Both triggers look up the target table name from `object_types` and run a dynamic `UPDATE` using `EXECUTE format(...)`.

### Auto-upvote on creation

When a post or comment is created, the author's vote is automatically inserted:

- **`trg_auto_upvote_post`** - fires `AFTER INSERT ON posts`. Inserts a `vote_value = 1` row in `votes` for the post's `author_id`, which in turn fires `trg_update_vote_score` and sets `vote_score` to `1`.
- **`trg_auto_upvote_comment`** - same behavior for `AFTER INSERT ON comments`.

This means new posts and comments start with a `vote_score` of `1` and the author always has an upvote on their own content.

## Stored functions

### `get_comment_tree`

Returns the comment tree for a given post, starting from top-level comments and recursing up to `p_max_depth` levels of replies.

```sql
get_comment_tree(
    p_post_id      UUID,
    p_max_depth    INTEGER DEFAULT 2,
    p_page_size    INTEGER DEFAULT 10,
    p_cursor_id    UUID    DEFAULT NULL,
    p_voter_id     UUID    DEFAULT NULL
)
```

- Top-level comments are paginated using keyset/cursor pagination on `(created_at, id)`. Pass `p_cursor_id` (the `id` of the last top-level comment on the previous page) to get the next page.
- Replies within each parent are fetched up to `p_page_size` per parent, ordered by `(created_at, id)`. They are not independently cursor-paginated; use `get_reply_tree` to page into a specific comment's replies.
- Returns columns: `id`, `post_id`, `parent_comment_id`, `author` (username), `body`, `created_at`, `updated_at`, `vote_score`, `depth`, `user_vote`.
- `depth` is `0` for top-level comments, incrementing with each level of nesting.
- `user_vote` reflects `p_voter_id`'s current vote on each comment (`1`, `-1`, or `0`); `0` when `p_voter_id` is `NULL`.

### `get_reply_tree`

Returns the reply tree rooted at a specific comment, recursing up to `p_max_depth` levels. The target comment itself is **not** included in the results.

```sql
get_reply_tree(
    p_post_id    UUID,
    p_comment_id UUID,
    p_max_depth  INTEGER DEFAULT 2,
    p_page_size  INTEGER DEFAULT 10,
    p_cursor_id  UUID    DEFAULT NULL,
    p_voter_id   UUID    DEFAULT NULL
)
```

- Returns an empty result set if the target comment does not exist or does not belong to the given post. Backends should interpret an empty result set on this function as a 404 signal (after verifying the comment exists separately).
- Direct replies (depth `1` relative to the target comment) are cursor-paginated the same way as `get_comment_tree`.
- Returns the same columns as `get_comment_tree`.
- `depth` starts at `1` for direct replies to the target comment.
