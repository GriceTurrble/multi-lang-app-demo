# Specification for frontend clients

A barebones Reddit-like application that lets users register, log in, browse Posts and Comments, and create/edit/delete their own content and votes.

## One directory per frontend

- Each sub-directory from here contains a STANDALONE frontend application that does not interact with the other frontends in any way.
- Each frontend should be following the SAME specification from this document.
- Each frontend should be interchangeable with any other at any time.

## Backend spec

Refer to the [Backend specification](../backends/SPEC.md) for the API contract each frontend must target.

## Requirements

Each frontend must fulfill the following criteria:

- Runs from a Docker container
- Communicates exclusively with a backend service API (no direct database access)
- All API requests to protected endpoints must include `Authorization: Bearer <token>` headers
- Provides pages for the resources and actions described below

## Authentication

Frontend clients implement a login/register/logout flow using the backend's session-based Bearer token system.

### Token storage

The session token received from `POST /auth/login` must be stored client-side and attached to all subsequent requests that require authentication. LocalStorage is an acceptable storage mechanism for this demo.

On application load, any stored token should be validated against `GET /auth/me`. If the token is invalid or expired, it must be cleared and the user treated as logged out.

### Auth state

The application must expose a global auth state containing:

- `user` — the authenticated user object (`id`, `email`, `username`) or `null`
- `token` — the current Bearer token string or `null`
- `login(token, user)` — stores token and user, persists to storage
- `logout()` — clears token and user from state and storage, calls `POST /auth/logout`

### Protected routes

The following routes require authentication. Unauthenticated users must be redirected to `/auth/login`:

- Create post
- Edit post (additionally, only the post's author may access this)
- Create comment
- Edit comment (additionally, only the comment's author may access this)
- Voting (requires auth; the vote is attributed to the authenticated user)

### Auth pages

- **Register** — `email`, `username`, `password` fields. On success, redirect to login.
- **Login** — `email`, `password` fields. On success, store token and redirect to posts list.
- **Logout** — Accessible from the site header when authenticated. Clears token and redirects to home.

## Pages / routes

### Public

- `/` — Home/welcome page with a link to browse posts
- `/posts` — Paginated list of posts (no auth required to view)
- `/posts/<post_id>` — Single post with threaded comment tree (no auth required to view)
- `/auth/register` — Registration form
- `/auth/login` — Login form

### Protected

- `/posts/new` — Create a new post
- `/posts/<post_id>/edit` — Edit an existing post (author only)

## Resource IDs

All resource IDs (e.g. `post_id`, `comment_id`, `user_id`) are [UUID v7] values generated by the backend.
Frontends must treat them as opaque strings.

## API client

The frontend API client must:

- Use a configurable base URL (e.g. via environment variable `NEXT_PUBLIC_API_BASE_URL` or equivalent)
- Attach `Authorization: Bearer <token>` to requests when a token is available
- Expose typed functions per resource matching the backend's REST contract
- Propagate HTTP error responses as structured errors available to UI components

## Votes

Votes are cast by authenticated users only. The vote is attributed server-side from the authenticated session; the frontend must **not** pass a `username` in the vote request body. The vote request body contains only:

- `value` — `1`, `0`, or `-1`

[uuid v7]: https://uuidv7.com
