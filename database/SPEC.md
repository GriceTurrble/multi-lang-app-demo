# Data specification

The schema every backend implementation shares.

A single Postgres instance backs the whole application. All backends read and write
the *same* tables, so the schema is part of the contract just as much as the REST
API is: a backend is only a drop-in replacement for another if it stores data the
same way.

The schema is not owned by any backend. It is defined as Diesel migrations in
[mlad-manage/mlad-manage-db-lib/migrations/](../mlad-manage/mlad-manage-db-lib/migrations/)
and applied with the `mlad-manage` CLI:

```sh
just manage run db migrate run
```

Fixture data for local development lives in
[mlad-manage/db_fixtures/fixtures.sql](../mlad-manage/db_fixtures/fixtures.sql) and
loads with `just manage run db load-fixtures`.

`tilt up` runs both of these for you.

Backends must **not** create, alter, or drop tables. A backend that needs a schema
change adds a migration to the shared crate so that every other backend gets it too.

## Identifiers

Every entity uses a [UUID v7] primary key, generated by Postgres via `uuidv7()` as a
column default. Backends should let the database assign ids rather than generating
them client-side. See [ADR 0001](../docs/adrs/0001-uuid-v7-for-identifiers.md) for
the reasoning.

Because UUID v7 values sort by creation time, `(created_at, id)` is a stable total
ordering and is what the keyset pagination in this spec uses.

The two readers walk that ordering in opposite directions, deliberately. The Posts
feed is newest first, so it opens on recent activity. Comment trees are oldest first,
so a conversation reads top to bottom.

## Tables

### `users`

| Column          | Type           | Notes                           |
| --------------- | -------------- | ------------------------------- |
| `id`            | `UUID`         | PK, defaults to `uuidv7()`      |
| `email`         | `VARCHAR(255)` | `UNIQUE NOT NULL`               |
| `username`      | `VARCHAR(100)` | `UNIQUE NOT NULL`               |
| `password_hash` | `TEXT`         | `NOT NULL`                      |
| `created_at`    | `TIMESTAMPTZ`  | defaults to `CURRENT_TIMESTAMP` |

`password_hash` holds a secure hash, never a plaintext password. See
[ADR 0002](../docs/adrs/0002-password-hashing-scheme.md) for the chosen scheme.
Backends must reject a duplicate `email` or `username` with `409 Conflict` rather
than surfacing the unique-violation error.

The `VARCHAR` widths are real limits. Validate input lengths in the backend so an
over-long value is a `422`, not a `500` from Postgres.

### `sessions`

| Column       | Type          | Notes                                             |
| ------------ | ------------- | ------------------------------------------------- |
| `id`         | `UUID`        | PK, defaults to `uuidv7()`; this *is* the token   |
| `user_id`    | `UUID`        | `NOT NULL REFERENCES users(id) ON DELETE CASCADE` |
| `created_at` | `TIMESTAMPTZ` | defaults to `CURRENT_TIMESTAMP`                   |
| `expires_at` | `TIMESTAMPTZ` | `NOT NULL`                                        |
| `is_active`  | `BOOLEAN`     | `NOT NULL DEFAULT TRUE`                           |

The session `id` is the Bearer token handed to the client as `access_token`. There is
no separate token column and no JWT: authentication is a lookup against this table.

A token is valid only when its row satisfies all three of:

- `id` matches the presented token
- `is_active = TRUE`
- `expires_at > NOW()`

Since the token is a UUID, a token that is not a well-formed UUID is simply an
invalid token. Backends must treat it as a `401`, not as a database error.

Deleting a user cascades their sessions away.

### `posts`

| Column       | Type          | Notes                                       |
| ------------ | ------------- | ------------------------------------------- |
| `id`         | `UUID`        | PK, defaults to `uuidv7()`                  |
| `title`      | `TEXT`        | nullable                                    |
| `body`       | `TEXT`        | `NOT NULL`                                  |
| `author_id`  | `UUID`        | `NOT NULL REFERENCES users(id)`             |
| `created_at` | `TIMESTAMPTZ` | defaults to `CURRENT_TIMESTAMP`             |
| `updated_at` | `TIMESTAMPTZ` | defaults to `CURRENT_TIMESTAMP`             |
| `vote_score` | `INTEGER`     | `NOT NULL DEFAULT 1`, maintained by trigger |

`author_id` has no cascade, so a user with posts cannot be deleted outright.

`updated_at` is *not* maintained by a trigger. Backends set it explicitly on update.
Clients use `updated_at != created_at` to decide whether to show an "edited" marker,
so an update that does not touch `updated_at` is a bug.

Do not write `vote_score` directly. See [Vote scoring](#vote-scoring).

### `comments`

| Column              | Type          | Notes                                                 |
| ------------------- | ------------- | ----------------------------------------------------- |
| `id`                | `UUID`        | PK, defaults to `uuidv7()`                            |
| `post_id`           | `UUID`        | `NOT NULL REFERENCES posts(id) ON DELETE CASCADE`     |
| `parent_comment_id` | `UUID`        | nullable, `REFERENCES comments(id) ON DELETE CASCADE` |
| `author_id`         | `UUID`        | `NOT NULL REFERENCES users(id)`                       |
| `body`              | `TEXT`        | `NOT NULL`                                            |
| `created_at`        | `TIMESTAMPTZ` | defaults to `CURRENT_TIMESTAMP`                       |
| `updated_at`        | `TIMESTAMPTZ` | defaults to `CURRENT_TIMESTAMP`                       |
| `vote_score`        | `INTEGER`     | `NOT NULL DEFAULT 1`, maintained by trigger           |

A comment with a `NULL` `parent_comment_id` is a **Top Comment**: a direct reply to
the Post. Any other comment is a **reply** to the comment it names.

The cascades do the deletion work described in the backend spec: deleting a Post
removes its whole comment tree, and deleting a Comment removes the subtree beneath
it. Backends should rely on the cascade rather than deleting recursively.

> [!IMPORTANT]
> The `parent_comment_id` foreign key only proves the parent comment exists
> *somewhere*. It does not prove the parent lives on the same Post.
>
> Backends **must** verify that a new reply's `parent_comment_id` belongs to the
> `post_id` in the request path. Without that check a reply can be attached across
> posts, producing a row that neither tree function will ever return.

### `object_types`

| Column       | Type           | Notes      |
| ------------ | -------------- | ---------- |
| `name`       | `VARCHAR(100)` | PK         |
| `table_name` | `VARCHAR(100)` | `NOT NULL` |

Seeded with exactly two rows:

| `name`      | `table_name` |
| ----------- | ------------ |
| `'Post'`    | `'posts'`    |
| `'Comment'` | `'comments'` |

This is the lookup side of the project's polymorphic-reference convention: where a
table carries a `..._object_id` / `..._object_type` pair, `object_type` resolves
through this table to the table holding the referenced row.

### `votes`

| Column        | Type          | Notes                                              |
| ------------- | ------------- | -------------------------------------------------- |
| `voter_id`    | `UUID`        | `NOT NULL REFERENCES users(id)`                    |
| `object_id`   | `UUID`        | `NOT NULL`, no FK (polymorphic)                    |
| `object_type` | `VARCHAR(20)` | `NOT NULL REFERENCES object_types(name)`           |
| `vote_value`  | `SMALLINT`    | `NOT NULL DEFAULT 1 CHECK (vote_value IN (1, -1))` |

`UNIQUE (object_id, object_type, voter_id)` gives one vote per user per object, and
is the conflict target for the upsert below.

Note the `CHECK`: **`0` is not a storable value.** The API accepts a `value` of `0`,
but it means "remove my vote", which is a `DELETE` of the row, not an update to `0`.

Applying a vote is therefore one of two statements:

```sql
-- value of 1 or -1
INSERT INTO votes (voter_id, object_id, object_type, vote_value)
VALUES ($1, $2, $3, $4)
ON CONFLICT (object_id, object_type, voter_id)
DO UPDATE SET vote_value = EXCLUDED.vote_value;

-- value of 0
DELETE FROM votes
WHERE voter_id = $1 AND object_id = $2 AND object_type = $3;
```

## Vote scoring

`posts.vote_score` and `comments.vote_score` are **derived columns**, kept correct by
database triggers. Backends read them and never write them.

| Trigger                           | Fires on                          | Effect                                                    |
| --------------------------------- | --------------------------------- | --------------------------------------------------------- |
| `trg_update_vote_score`           | `AFTER INSERT OR UPDATE ON votes` | Recomputes the target's `vote_score` as `SUM(vote_value)` |
| `trg_update_vote_score_on_delete` | `AFTER DELETE ON votes`           | Same recomputation, using the deleted row                 |
| `trg_auto_upvote_post`            | `AFTER INSERT ON posts`           | Inserts a `+1` vote from the author                       |
| `trg_auto_upvote_comment`         | `AFTER INSERT ON comments`        | Inserts a `+1` vote from the author                       |

The two auto-upvote triggers are why `vote_score` defaults to `1`: a new Post or
Comment starts with its author's own upvote already recorded in `votes`. That vote is
a real row, so the author can later remove it with a `value` of `0`, taking the score
to `0`.

Both scoring triggers resolve the target table through `object_types` and raise
`'Unknown object_type: %'` for a value not found there.

The practical consequence: after applying a vote, a backend should re-read
`vote_score` from the target table to build its response. Computing the score in
application code will drift from what the triggers store.

## Stored functions

Comment trees are read through two stored functions rather than assembled in
application code, so that every backend paginates and orders them identically.

Both return a **flat** table of rows carrying a `depth` column. They do not return
nested structures. Assembling the tree from `parent_comment_id` is the client's job.

Both return these columns:

`id`, `post_id`, `parent_comment_id`, `author` (the username, not the id), `body`,
`created_at`, `updated_at`, `vote_score`, `depth`, `user_vote`

`user_vote` is the calling user's own vote on that comment, or `0` when they have not
voted or are anonymous. It comes from the `p_voter_id` argument, which is `NULL` for
an unauthenticated request.

Rows are ordered by `depth`, then `created_at ASC`, then `id ASC`.

### `get_comment_tree`

```sql
get_comment_tree(
    p_post_id   UUID,
    p_max_depth INTEGER DEFAULT 2,
    p_page_size INTEGER DEFAULT 10,
    p_cursor_id UUID    DEFAULT NULL,
    p_voter_id  UUID    DEFAULT NULL
)
```

Returns the Top Comments of a Post, with replies expanded recursively up to
`p_max_depth` levels. Top Comments have `depth = 0`.

Pagination is keyset-based over Top Comments only: pass the `id` of the last
`depth = 0` row from the previous page as `p_cursor_id`, or `NULL` for the first
page. Replies are *not* cursor-paginated here; `get_reply_tree` covers that.

`p_max_depth = 0` returns Top Comments alone.

### `get_reply_tree`

```sql
get_reply_tree(
    p_post_id    UUID,
    p_comment_id UUID,
    p_max_depth  INTEGER DEFAULT 2,
    p_page_size  INTEGER DEFAULT 10,
    p_cursor_id  UUID    DEFAULT NULL,
    p_voter_id   UUID    DEFAULT NULL
)
```

Returns the replies beneath a single Comment. The target comment itself is **not**
included. Direct replies have `depth = 1`, so the depth base differs from
`get_comment_tree`. Backends reading the next cursor must filter on `depth = 1` here
and `depth = 0` there.

If the target comment does not exist, or exists but belongs to a different Post, the
function returns an **empty result set** rather than raising. An empty result is
therefore ambiguous: it means either "no replies" or "no such comment". Backends must
disambiguate with a follow-up existence check before deciding between `200` and
`404`.

### Bounding the tree queries

Both functions expand recursively, so an unbounded `p_max_depth` and `p_page_size`
let a single request ask for an arbitrarily large tree. Backends must validate these
parameters before passing them through, rejecting out-of-range values with `422`.

[uuid v7]: https://uuidv7.com
